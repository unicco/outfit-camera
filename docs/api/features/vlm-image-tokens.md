# VLM に送る画像サイズと課金トークン

`src/coordinate_recorder/vlm_clothing_detector.py` が VLM へ送る画像の長辺上限（`MAX_PHOTO_EDGE` /
`MAX_WARDROBE_EDGE`）を、なぜその値にしたかの記録。2026-08-19 に調査。

## 結論

**一律のダウンスケールは Gemini のトークンを減らさない。**入れているのは削減ではなく、
上限のない入力に対するガード。

**2026-08-21 に本番で after を実測し、この読みどおりだった。**導入前（8/6〜8/15 の 11 回）と
導入後（8/21）がともに入力 14,069 トークンで一致した。トークンが 1 つも減っていない＝
`MAX_WARDROBE_EDGE` は 1 枚も縮めていないので、削減効果ゼロで正しい。

言えるのはここまで。**フォールバック経路そのものは観測していない**ので、「原寸で送られた
アイテムが 0 件だった」とまでは言えない（384px 以下の原寸なら縮めても 258 トークンの下限に
当たり、トークンには表れない）。区別が要るなら経路にログを足す。

⚠️ **14,069 は時点の観測値であって不変量ではない。**ワードローブに 1 枚足せば上がる（下の
「コストの実勢」）。ここで確かめたのは「前後で一致した」ことだけで、この数値そのものを
基準にしない。

## Gemini と Claude で課金式が違う

**このリポの VLM は Gemini だけ**（Claude 経路は  で撤去した）。
以下の表は、送信画像のサイズを別プロバイダで検討し直すときに
Gemini との違いを取り違えないための記録。

| | Gemini 2.5 Flash | Claude（standard tier） |
|---|---|---|
| 単位 | 768×768 の tile ごとに 258 トークン | 28×28 パッチごとに 1 visual token |
| tile / パッチ数 | `crop = floor(min(w,h)/1.5)` → `ceil(w/crop)×ceil(h/crop)` | `ceil(w/28)×ceil(h/28)` |
| 下限 | 両辺 384px 以下なら 258 トークン | — |
| 上限 | crop は 768px で頭打ち | 長辺 1568px・1568 トークンへ自動縮小 |

Gemini の crop unit は短辺に比例するので、**同じアスペクト比のまま縮めても tile 数が変わらない**。

| 画像 | Gemini | Claude |
|---|---|---|
| 1920×1080 | 6 tile = 1,548 | 1456×819 へ自動縮小 → 1,560 |
| 1280×720 | 6 tile = **1,548**（変わらない） | 1,196 |
| 4032×3024 | 24 tile = **6,192** | 1,560 |
| 200×200 | 258（下限） | 64 |

短辺が 1152px（= 768×1.5）を超えると crop が頭打ちになり、そこから先はダウンスケールが効く。

出典: [Gemini image understanding](https://ai.google.dev/gemini-api/docs/image-understanding) /
[Claude vision](https://platform.claude.com/docs/en/build-with-claude/vision)

## 上限値の根拠

| 定数 | 値 | 効く相手 |
|---|---|---|
| `MAX_PHOTO_EDGE` | 2048 | `POST /detect-file` に上がる大きな写真。Pi の撮影（1920×1080）は画素が変わらない |
| `MAX_WARDROBE_EDGE` | 384 | `thumb_200` を持たないアイテムの原寸フォールバック（`routers/ai_detection.py`）。1,032〜1,548 → 258 トークン |

`thumb_200` は 200×200 で既に Gemini の下限に達しており、縮めても減らない。二重圧縮を避けるため
上限内のバイト列は再エンコードせず原本を送る。

## 触っていないもの

- **保存する画像**: 縮めるのは送信直前のエンコードだけ。GCS のオリジナルもサムネイルも無変更
- **bbox の座標系**: `routers/ai_detection.py` は元の numpy 配列から `h, w` を取る。ペイロードを
  縮めても座標は元寸のまま
- **左右反転**: VLM 経路は反転処理を通らない（反転は Pi の `Transform`  側）。
  リサイズと鏡像反転は可換なので順序の問題も起きない

## コストの実勢

1 リクエスト = ワードローブ枚数 N × 258 + 全身写真 1,548。Gemini 2.5 Flash の入力は $0.30/1M
なので、N=100 でも約 27,000 トークン ≒ $0.008。**支配項は解像度ではなく N。**

本番ログでも解像度は効いていない: 写真は一貫して Pi の 1920×1080 なのに、入力は 8/1 の 12,999
から 8/5 に 13,535 → 14,069 と 2 段上がり、以降 8/21 まで 14,069 で動かない。動くのは N の側だけ
（増分は 2 回とも約 535）。現状 1 回 14,069 トークン ≒ $0.0042。

⚠️ 金額の前提は **`gemini-2.5-flash` の入力 $0.30/1M（2026-08-21 時点の paid tier）**。単価も
モデルも動くので、**金額を引くときはこの 2 つを確かめ直す**（モデルの世代を上げる検討は
）。
